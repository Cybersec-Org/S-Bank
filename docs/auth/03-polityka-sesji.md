# Polityka sesji – etap 3 (2026-11-25)

Ważność tokenów, 2FA, limit nieudanych logowań i zachowanie aplikacji.

**Źródła:**

- decyzje z `docs/auth/01-decyzje.md` (D1–D21, P-01–P-12, zatwierdzone 2026-11-25);
- elementy sesji z `docs/auth/02-elementy-sesji.md`;
- żywy realm `sbank` (odczyt `kcadm` 2026-11-25);
- `REQUIREMENTS.md` (SR-xx, model zagrożeń T-xx);
- dokumenty z zajęć: `docs/BASIM4/d3_decyzje_o_magazynie.md`, `d4_mapa_kana_w_wycieku.md`, `d5_polityka_sesji.md` (gałąź `BASIM-main`).

**Kolumna „Stan”:**

- **zgodne** – realm / kod już tak działa;
- **różnica** – dziś jest inaczej; obok podana zatwierdzona propozycja albo etap, który to zmienia;
- **do zrobienia** – brak w kodzie, zaplanowane.

## 3. Zachowanie aplikacji – reguły

1. **Logowanie** tylko w przeglądarce systemowej (`expo-web-browser` / `expo-auth-session`), nigdy w WebView. Aplikacja nie widzi hasła ani kodu TOTP (SR-01).
2. **„Zaloguj się hasłem”** wysyła `acr_values=1`. **„Zaloguj się kluczem dostępu”** wysyła `acr_values=2`. **Step-up** wysyła `acr_values=2`, a od etapu 9 także `prompt=login` i `max_age=0`.
3. **Pracownik lub administrator z tokenem `acr=1`**, np. po pierwszym logowaniu z rejestracją klucza, dostaje z API 403 `PASSKEY_REQUIRED`. Aplikacja pokazuje „Zaloguj się kluczem dostępu” zamiast ogólnego błędu (etap 9).
4. **Przy 401** aplikacja odświeża token najwyżej raz, a wszystkie równoległe żądania czekają na to jedno odświeżenie. Druga odmowa oznacza wylogowanie lokalne bez pytania (etap 10).
5. **Bez `console.*`** z tokenami, kodami, kwotami, IBAN-ami i treścią odpowiedzi API (BASIM4 D4: kanał „Logi”).
6. **Ukrywanie ekranów** (podział platform, strażnicy tras) to tylko wygoda. Role, właściciela zasobu, limity i próg 1 000 zł sprawdza API (SR-05).
