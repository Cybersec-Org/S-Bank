# REQUIREMENTS – S-Bank

Dokument wymagań projektu S-Bank: cel aplikacji, użytkownicy, wymagania funkcjonalne, wymagania bezpieczeństwa i model zagrożeń. Schemat działania aplikacji jest w [docs/diagramy.md](docs/diagramy.md), a lista zadań w [BACKLOG.md](BACKLOG.md).

## 1. Cel aplikacji

S-Bank to prosta aplikacja bankowa działająca w przeglądarce i na telefonie (Android, iOS). Pozwala założyć konto, zalogować się, sprawdzić saldo i historię operacji, wykonać przelew, zapłacić kodem QR lub linkiem płatności oraz sprawdzić kursy walut NBP.

| Pytanie                             | Odpowiedź                                                                                                                                                                                                                                                                             |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Jaki problem rozwiązuje?            | Klient chce szybko i bezpiecznie zarządzać pieniędzmi z telefonu i z komputera, bez instalowania kilku osobnych narzędzi. Jednocześnie aplikacje bankowe są jednym z głównych celów ataków (phishing, przejęcie konta, kradzież sesji), więc wygoda nie może obniżać poziomu ochrony. |
| Kto będzie z niej korzystał?        | Klienci indywidualni banku, pracownicy obsługi klienta, administrator oraz partnerzy (np. sklepy internetowe), którzy przez API wystawiają klientom żądania płatności.                                                                                                                |
| Dlaczego jest potrzebna?            | Pokazuje na działającym przykładzie, jak zbudować usługę finansową z gotowych, zaufanych mechanizmów bezpieczeństwa: logowania OIDC, kluczy dostępu (passkeys), mTLS, HSM przez PKCS#11 i kontroli dostępu po stronie serwera.                                                        |
| Jaką podstawową czynność umożliwia? | **Wykonanie przelewu z własnego rachunku** – z kontrolą limitu dziennego i dodatkowym potwierdzeniem kluczem dostępu dla większych kwot.                                                                                                                                              |

## 2. Użytkownicy i ich możliwości

| Użytkownik                                    | Możliwości                                                                                                                                                                           | Ograniczenia                                                                                                                   |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| **Gość** (niezalogowany)                      | rejestracja, kursy walut i przelicznik, regulamin, lista bankomatów                                                                                                                  | brak dostępu do jakichkolwiek danych klientów; limit liczby zapytań                                                            |
| **Klient** (`customer`)                       | logowanie hasłem lub kluczem dostępu, własne rachunki i historia, przelewy w ramach limitu, odbiorcy, płatności z kodu QR lub linku, potwierdzenia przelewów, odblokowanie biometrią | widzi i zmienia wyłącznie własne dane; przelew od 1 000 zł wymaga potwierdzenia kluczem dostępu; nie zmieni sobie limitu       |
| **Pracownik banku** (`employee`)              | wyszukiwanie klientów, podgląd rachunków i historii (tylko odczyt), blokada i odblokowanie rachunku, zmiana limitu dziennego                                                         | nie zleca przelewów, nie zmienia sald, nie nadaje ról, nie czyta dziennika audytowego; logowanie wyłącznie kluczem dostępu     |
| **Administrator** (`admin`)                   | zarządzanie kontami i rolami, rejestracja partnerów API i ich certyfikatów, odczyt dziennika audytowego, parametry globalne (próg step-up, zakres limitów)                           | nie zleca przelewów, nie zmienia sald, nie modyfikuje dziennika audytowego                                                     |
| **Partner API** (`partner`, klient maszynowy) | tworzenie żądań płatności na własny rachunek, sprawdzanie ich statusu                                                                                                                | brak dostępu do danych klientów; nie zatwierdza płatności za klienta; połączenie tylko z certyfikatem wystawionym przez S-Bank |

Pełna tabela „co może / czego NIE może” jest w karcie projektu w [README.md](README.md) i jest podstawą testów autoryzacji.

## 3. Wymagania funkcjonalne

Priorytet **MVP** oznacza funkcję potrzebną na zajęcia 5, **R** – rozszerzenie po MVP.

| ID    | Wymaganie                                                                                                                                                                                                                              | Użytkownik    | Priorytet               |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- | ----------------------- |
| FR-01 | **Rejestracja.** Gość zakłada konto, podając imię, nazwisko, e-mail i hasło. Konto staje się aktywne po potwierdzeniu adresu e-mail, a system zakłada dla niego rachunek demonstracyjny z saldem początkowym.                          | Gość          | MVP                     |
| FR-02 | **Logowanie i wylogowanie.** Użytkownik loguje się hasłem albo kluczem dostępu (passkey). Wylogowanie kończy sesję w aplikacji i na serwerze tożsamości.                                                                               | wszyscy       | MVP                     |
| FR-03 | **Pulpit.** Po zalogowaniu klient widzi swoje rachunki z saldem, wykorzystanie limitu dziennego i ostatnie operacje.                                                                                                                   | Klient        | MVP                     |
| FR-04 | **Historia operacji.** Klient przegląda historię swojego rachunku z filtrowaniem po dacie i rodzaju operacji.                                                                                                                          | Klient        | MVP                     |
| FR-05 | **Przelew.** Klient zleca przelew na numer rachunku (IBAN) z tytułem i kwotą. System sprawdza poprawność numeru, saldo i limit dzienny, pokazuje podsumowanie i wymaga potwierdzenia; od 1 000 zł potwierdzenie wymaga klucza dostępu. | Klient        | MVP                     |
| FR-06 | **Odbiorcy.** Klient zapisuje, edytuje i usuwa odbiorców, a przy przelewie wybiera odbiorcę z listy.                                                                                                                                   | Klient        | MVP                     |
| FR-07 | **Płatność z kodu QR lub linku.** Klient skanuje kod QR albo otwiera link płatności; aplikacja pobiera z serwera dane żądania partnera, a klient je zatwierdza lub odrzuca.                                                            | Klient        | MVP                     |
| FR-08 | **Kursy walut.** Każdy, także bez logowania, widzi aktualne kursy średnie NBP i przelicza kwotę w złotych na wybraną walutę.                                                                                                           | wszyscy       | MVP                     |
| FR-09 | **Panel pracownika.** Pracownik wyszukuje klienta, podgląda jego rachunki i historię, blokuje lub odblokowuje rachunek i zmienia limit dzienny w dozwolonym przedziale.                                                                | Pracownik     | MVP                     |
| FR-10 | **API partnerskie.** Partner tworzy żądanie płatności (kwota, tytuł, czas ważności) i sprawdza jego status.                                                                                                                            | Partner       | MVP                     |
| FR-11 | **Potwierdzenie przelewu.** Po wykonaniu przelewu klient pobiera potwierdzenie podpisane cyfrowo przez bank, które da się zweryfikować kluczem publicznym banku.                                                                       | Klient        | MVP (wersja podstawowa) |
| FR-12 | **Panel administratora.** Administrator zarządza rolami użytkowników, partnerami API i ich certyfikatami oraz przegląda dziennik audytowy.                                                                                             | Administrator | MVP                     |
| FR-13 | **Bankomaty w pobliżu.** Aplikacja mobilna pokazuje listę bankomatów posortowaną według odległości od użytkownika (za jego zgodą na lokalizację).                                                                                      | Klient        | MVP                     |
| FR-14 | **Bezpieczeństwo konta.** Klient włącza odblokowanie aplikacji biometrią oraz dodaje i usuwa swoje klucze dostępu.                                                                                                                     | Klient        | R                       |

Funkcje dostępne **tylko po zalogowaniu**: FR-03 – FR-07, FR-09 – FR-12 i FR-14.

## 4. Wymagania bezpieczeństwa

Odniesienia: kategorie [OWASP MASVS](https://mas.owasp.org/MASVS/) oraz [OWASP API Security Top 10 – 2023](https://owasp.org/API-Security/editions/2023/en/0x11-t10/) (oznaczenia API1–API10).

| ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | --------------------- |
| SR-01 | Uwierzytelnianie wyłącznie przez OpenID Connect (Authorization Code + PKCE) w przeglądarce systemowej; aplikacja nigdy nie przetwarza hasła. Adresy przekierowań są zarejestrowane dokładnie, bez symboli wieloznacznych.                                                                                  | Keycloak, expo-auth-session, expo-web-browser                               | test e2e logowania; przegląd eksportu konfiguracji realmu                                      | MASVS-AUTH, API2      |

| SR-03 | Klucze dostępu (passkeys) jako metoda logowania; przelew od 1 000 zł oraz każde logowanie pracownika i administratora wymaga wyższego poziomu uwierzytelnienia (step-up). **API samo sprawdza** poziom `acr` i czas uwierzytelnienia `auth_time` w tokenie.                                                | Keycloak: WebAuthn Passwordless, poziomy LoA; jose w API                    | test: token z niskim `acr` dostaje 403 przy przelewie 1 000 zł                                 | MASVS-AUTH, API6      |

API sprawdza podpis (tylko dozwolone algorytmy), wystawcę, odbiorcę i ważność.                                                                                                              | Keycloak, jose (JWKS)                                                       | testy: token wygasły, z obcym `aud`, z `alg: none` – odrzucone                                 | MASVS-AUTH, API2      |

## 6. Model zagrożeń

Kategorie według STRIDE: **S** – podszycie się, **T** – manipulacja danymi, **R** – wyparcie się, **I** – ujawnienie informacji, **D** – odmowa usługi, **E** – podniesienie uprawnień.
